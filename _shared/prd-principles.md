# What a good PRD looks like here

Read by `release-prd` (`02_problem`, `03_scope`, `04_prd`) and `feature-prd` (`01_behaviour`,
`02_spec`). The starting
tests below are generic. Replace or sharpen them with your own.

> **STATUS: STARTER.** Until you edit this, the PRD pipelines run on generic practice. Add what you
> reject on sight in your organisation's PRDs.

## Tests a PRD must pass

1. **One problem, with evidence.** The problem is stated once, with its source. An unsourced claim
   is labelled as an assumption.
2. **One metric that moves.** It names the metric, the current value and the target.
3. **Scope is a decision.** What is out is listed as clearly as what is in, with the reason.
4. **Short enough to stay true.** It points at decisions and feature PRDs; it does not copy them.
   A PRD that repeats its sources goes stale with every revision.
5. **Every state has an outcome** (feature PRDs). Nothing is left for the builder to invent.
6. **Every acceptance criterion is a test** (feature PRDs). Given, when, then.

## Failure modes to name out loud

- **Solution looking for a problem.** The feature is clear; the evidence is not.
- **The everything PRD.** One document that tries to be strategy, scope and spec at once.
- **Happy path only.** Errors, permissions and empty states are missing.
- **Silent assumption.** A gap in the sources filled without saying so.
